# ADR-002：数据库迁移管理与开发工作流

日期：2026-10-11 ｜ 状态：已接受

## 背景

v1 的 schema 建表写在 `Db` 构造函数里（内联 MIGRATIONS 数组），服务启动即隐式建表。
发版需要可审计、可预检、可回滚准备的显式迁移；开发需要热重启。

## 决策

1. **迁移目录制**：`packages/server/migrations/NNN-名称.sql`，按序号即版本。
   每个迁移在事务内执行，失败回滚且不落版本号；版本记录于 `meta.schema_version`。
2. **显式迁移，双保险**：
   - `npm run migrate` 是唯一自动迁移入口（幂等）；
   - `npm start` / Docker CMD / `npm run dev` 都先跑它；
   - 服务入口带 schema 守卫：库落后则拒启，报错指明 `npm run migrate` 与待应用文件。
   - `npm run migrate:status` 只读预检（落后退出码 2，供部署流水线 gate）。
3. **内容包不走 schema 迁移**：内容是按 sha 幂等种子化的数据域（技术架构 §6），
   与结构迁移分离；两者都在启动序内完成。
4. **开发热重启**：`npm run dev` = 迁移 + `node --watch`（模块图监视）。
   改 `packages/*.js` 即重启并重新走迁移+守卫。**不使用 `--watch-path` 扩展监视**：
   实测该模式会把进程打开的数据库 WAL 文件（`-shm`）纳入监视，每次写库都触发重启；
   模块图模式写库零重启。内容包改动用 watch 的 `rs` 手动重启（内容启动时种子化）。
   开发入口复用生产入口 `createApp`（同一条代码路径）。
5. **运维基线**：配置中心（env 单入口 + fail-fast 校验）、结构化 JSON 日志、
   SIGTERM 优雅关停（WAL checkpoint）、输入限流（env 可调）、会话 TTL、
   `npm run backup`（VACUUM INTO 快照 + 保留策略）、healthz 汇报 app/schema/pack 三版本。

## 后果

- 新增 schema 变更 = 落一个 `NNN-*.sql` 文件（PR 可评审的 diff），运行 `npm run migrate`。
- 测试里 `createApp` 之前必须 `applyMigrations`（e2e 已按部署等价路径书写）。
- compose 增加 `init: true` 保证信号转发，配合优雅关停避免 WAL 残留。
