> 配套文档：[GDD-v0.1.md](./GDD-v0.1.md)（游戏设计方案）

> 定位：**为"以小块为单位的迭代、评审、测试"而设计**的工程方案。
> 每一个数值、每一句提示词、每一条暗线，都必须能在不改代码、可回滚、

## 1. 设计目标与工程原则

本项目的第一风险不是"写不出来"，而是"改不动"。游戏设计会在几十次评审中
反复推翻重调，因此架构把**变化频率**作为第一切分依据：

| 变化频率 | 内容 | 载体 |
|---|---|---|
| 每周都在改 | 数值、物价、事件权重、提示词、文案模板 | **内容包（数据）** |
| 每月都在改 | 新机制、新地点、新角色 | 内容包 + 少量内核注册代码 |
| 很少改 | 状态机骨架、时间槽、检定协议 | **内核（代码）** |
| 从不改 | "LLM 提议、内核裁决、LLM 演出"的总契约 | 架构宪法 |

工程原则（所有 PR 按此评审）：

1. **内核纯函数化**：游戏内核不碰 I/O、不碰 LLM、不碰时间。
   同输入 + 同种子 → 同输出。这是确定性测试和平衡模拟的前提。
2. **内容即数据**：一切设计参数住在内容包里（JSON），PR 里以 diff 形式被评审，
   数据库按版本种子化，历史对局可按旧版本重放。
3. **测试即设计**：每个机制先写"业务场景测试"（用游戏语言描述），
   平衡性不是感觉，是流水线上带阈值的门禁。
4. **LLM 可拔插**：LLM 全挂时游戏仍可玩（直读模式）；
   全部 e2e 测试不依赖真实 LLM。
5. **单体部署，模块化单体**：单 Docker、单 SQLite、单 Node 进程；
   内部按 workspace 严格分层，禁止反向依赖。

## 2. 总体架构

```
┌────────────────────────── 浏览器 ──────────────────────────┐
│  web (React SPA)：三段式界面 / 档案馆 / 管理后台            │
└───────────────┬────────────────────────────────────────────┘
                │ REST + SSE（叙事流式返回）
┌───────────────▼────────────────────────────────────────────┐
│                    server (Fastify)                         │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────────────┐  │
│  │ 会话编排     │  │ LLM 网关      │  │ 管理面            │  │
│  │ SessionOrch │→ │ Provider 抽象 │  │ 内容/LLM/模拟/回放 │  │
│  └──────┬──────┘  │ DeepSeek/GLM │  └───────────────────┘  │
│         │ 意图     └──────────────┘                          │
│  ┌──────▼───────────────────────────────────────────────┐  │
│  │ core（纯函数内核）                                     │  │
│  │  状态机 / 日循环 / 探索与检定 / 事件与袭击 / 心情道德    │  │
│  └──────┬───────────────────────────────────────────────┘  │
│         │ 事件流（event sourcing）                          │
│  ┌──────▼──────┐   ┌────────────┐   ┌──────────────────┐   │
│  │ store       │   │ content    │   │ sim（无头模拟器）  │   │
│  │ SQLite      │   │ 内容包加载  │   │ 平衡性蒙特卡洛     │   │
│  └─────────────┘   └────────────┘   └──────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**核心数据流（一次玩家输入）**：

```
玩家自然语言
  → server: 会话编排
  → LLM①(裁判): 解析 → 意图列表(JSON)          ← 可被直读模式/测试桩替换
  → core: 校验意图 → 扣行动点/时间槽 → 掷骰 → 结算
       → 产出: 结构化结果枚举 + 叙事事实(facts)
  → LLM②(叙事者/演员): facts → 叙事文本(流式)
  → server: 事件写库 + 快照更新 → SSE 推送
```

LLM 在链路里出现两次、都被内容包中的提示词模板驱动、都只产出**文本或结构化建议**，
对游戏状态的写入权为零。

## 4. 内核设计（packages/core）

### 4.1 纯函数 + 种子随机

```ts
// 所有入口的统一形状
resolve(state: GameState, intents: Intent[], rng: Rng): Resolution
// Resolution = { events: GameEvent[], facts: Fact[], state: GameState', rolls: RollLog }
```

- 随机数由调用方注入（`seedrandom` 风格，run 级种子 + 事件序号派生），
  内核自身不产生任何不确定性 → **任何一局可逐帧重放**。
- 掷骰显式记录进 `RollLog`（玩家"透明模式"与管理员回放器都读它）。
- 时间不进内核：内核只有"阶段推进"概念，由编排层调用。

### 4.2 意图协议（LLM 与内核之间唯一的桥）

```ts
// packages/shared/intent.ts —— zod schema，双边共享
type Intent =
  | { type: 'act'; actor: CharId; action: 'eat'|'craft'|'build'|'treat'|'talk'|'guard'|'sleep'; target?: string; count?: number }
  | { type: 'scavenge-move'; to: RoomId }
  | { type: 'scavenge-search'; container: ContainerId }
  | { type: 'dialogue'; to: NpcId; say: string }        // 仅原文透传给演员
  | { type: 'plan'; steps: Intent[] }                    // 计划模式展开结果
  | { type: 'meta'; query: 'status'|'inventory'|... };

// 内核拒绝时给出结构化原因，供裁判 LLM 转译成人话
type Rejection = { intent: Intent; reason: 'NO_ITEM'|'NO_AP'|'NEED_TOOL'|'SEALED'|'OUT_OF_BOUND'|... };
```

**测试含义**：意图 schema 是 e2e 的断言层——测试不检查叙事文本，
检查"这句话应该被解析成这个意图、内核应该接受/拒绝"。

### 4.3 事件溯源（event sourcing）

- 对局的唯一事实源是事件表；`GameState` 是事件的折叠（fold）结果。
- 每个游戏日结束落一张快照（加速读取），快照可随时从事件重建并断言一致。
- 用途：① 玩家报告 bug 时按 run 重放；② 平衡分析直接 SQL 查事件表
  （"全服饿死事件按天分布"）；③ 档案馆跨局数据从事件派生。

事件目录（节选）：`RunStarted / DayStarted / IntentAccepted / IntentRejected /
RollMade / ItemMoved / HungerTicked / MoodChanged / RaidResolved /
LocationEntered / NpcMet / CanonDocSeen(封印解锁) / CharDied / WarEnded / RunEnded`。

## 5. 内容与参数体系（packages/content + content/）

- 内容包带 **semver**，一个 run 永远绑定其开局时的 `contentVersion` → 旧局重放永不失真。
- 启动时内容包经 zod schema 全量校验后种子化进 SQLite；校验失败拒绝启动
  （引用完整性：配方引用的物品必须存在、地点引用的文档必须在 docs.json……）。
- `canon.json` 里的封印档案单独表存储，**按需注入** LLM 上下文（见 §7.5），
  不进任何常规提示词。
- 数值评审工作流：改 `items.json` 物价 → PR 自动跑平衡模拟 → 报告贴在 PR →
  评审合并 → 内容包升版本。**设计迭代零代码改动。**

## 6. 数据库设计（SQLite，WAL 模式）

单库双域：内容域（可由内容包重建）+ 玩家域（不可再生）。
表结构（节选）：

```sql
-- ── 内容域 ─────────────────────────────
content_pack(id, semver, manifest_json, imported_at)
content_entity(pack_id, kind, key, data_json)
  -- kind: item|recipe|character|location|event|doc|prompt|narration|kpi
canon_seal(pack_id, seal_key, trigger_json, payload_enc)   -- 封印档案

-- ── LLM 配置域 ─────────────────────────
llm_provider(id, name, adapter,        -- 'openai-compat' | 'anthropic-compat'
             base_url, model, api_key_enc, params_json, enabled)
llm_route(purpose,          -- 'referee'|'narrator'|'actor'
          provider_id, fallback_provider_id, overrides_json)
llm_health_log(id, provider_id, ok, latency_ms, detail_json, at)
llm_call_log(id, purpose, provider_id, tokens_in, tokens_out,
             latency_ms, cost_estimate, run_id, at)        -- 观测与成本

-- ── 玩家域 ─────────────────────────────
user(id, name, pass_hash, is_admin, created_at)
run(id, user_id, seed, content_pack_id, difficulty, mode, -- mode: 'llm'|'direct'
    status, ending_type, started_at, ended_at)
run_event(run_id, seq, type, data_json, at)               -- 事件溯源主表
run_snapshot(run_id, day, phase, state_json)              -- 物化快照
archive_entry(user_id, kind, key, data_json, first_run_id, at)
  -- kind: doc|npc_truth|reputation|run_memory|ending     -- 档案馆跨局
setting(key, value)
```

- better-sqlite3 + Drizzle ORM（typed schema + 迁移）；WAL；单进程单写者，够用。
- `api_key_enc`：AES-256-GCM，主密钥来自环境变量；管理界面只写不回显。
- 备份：每日 `VACUUM INTO` 快照 + 保留策略；文档给出 litestream 可选方案。
- **数据成长测试**专项覆盖：事件表体积（一局 60 天 ≈ 3-8k 事件）在 500 局后
  的快照重建耗时、档案馆查询、迁移幂等性（见 §10 L5）。

## 7. LLM 层（packages/llm）

### 7.1 Provider 抽象

两个适配器类覆盖 DeepSeek 与 GLM（均为 OpenAI 兼容协议）；
GLM coding plan 若走 Anthropic 兼容端点，则用第二个适配器：

```ts
interface LLMProvider {
  meta: { id: string; adapter: 'openai-compat' | 'anthropic-compat' };
  chat(req: ChatRequest): Promise<ChatResult>;        // 非流式（裁判用，JSON 输出）
  stream(req: ChatRequest): AsyncIterable<Delta>;     // 流式（叙事者用）
  health(): Promise<HealthReport>;                    // 连通性测试
}
```

内置预设（管理员可改可新增自定义）：

| 预设 | adapter | baseURL | 常用模型 |
|---|---|---|---|
| DeepSeek | openai-compat | `https://api.deepseek.com` | deepseek-chat / deepseek-reasoner |
| GLM 开放平台 | openai-compat | `https://open.bigmodel.cn/api/paas/v4` | glm-4 系列 |
| GLM Coding Plan | anthropic-compat | 按 coding plan 端点配置 ★ | 订阅内模型 |
| 自定义 | 任一 | 任意 | 任意 |

### 7.2 按用途路由 + 降级链

- 路由按**用途**配置：`referee`（意图解析，低温、JSON 输出、可用便宜快速模型）
  / `narrator`（叙事，温度稍高）/ `actor`（NPC 对话）。
  每个用途可指定主 provider + fallback provider。
- 失败策略：超时 2 次重试 → 切 fallback → 全部失败则**降级直读模式**——
  用 `narrations/` 模板库把结果枚举渲染成文字，游戏继续可玩，
  顶部提示"叙事引擎离线"。内核永不被 LLM 故障阻塞。

### 7.3 结构化输出（裁判专用）

- 请求 `response_format: json_object`（两家均支持；不支持时走提示词约束）。
- 返回经 zod 校验；解析失败 → 携带错误信息重试一轮 → 仍失败 →
  要求玩家换个说法（把 LLM 的不稳定转化为一次体面的追问，而不是崩溃）。

### 7.4 连通性测试（管理后台功能）

- 每个 provider 一个「测试」按钮：后端真实调用（约 20 token 的 ping prompt），
  记录 `ok / 延迟 / 模型回显 / token 用量 / 错误原文` 入 `llm_health_log`。
- 页面展示历史曲线；支持「测试全部路由」一键体检。
- 测试用后端出口（不暴露 key 给浏览器）；失败信息展示原始 HTTP 错误便于排障。

### 7.5 提示词注册表与知识封印

- 提示词模板存 `content/base/prompts/`，DB 内带 sha 版本，改模板走 PR + 金样本测试。
- **封印注入协议**：常规上下文只含"角色已知信息"；内核在事件
  `CanonDocSeen` / 特定触发器满足时，把 `canon_seal.payload` 注入当次调用的
  上下文。封印内容永不进入常规模板 → 模型在条件未满足时确实不知道，
  玩家套话无效（这是可测试的，见 §10 L4 泄漏测试）。

### 7.6 观测

- 每次 LLM 调用记录用途/耗时/token/成本估算（`llm_call_log`），
  管理后台出"每局成本"报表——文字游戏的成本模型必须从第一天就可见。

## 8. API 设计（Fastify）

```
# 游戏
POST /api/runs                     开局 {difficulty, seed?, mode}
GET  /api/runs/:id                 当前快照 + 状态栏数据

GET  /api/runs/:id/events?from=seq 事件流（前端断线恢复）
POST /api/runs/:id/settings        日常委托/透明模式等

# 档案馆
GET  /api/archive                  文档/人物真相/这座城记得/进度

# 管理面（admin 鉴权）
GET|POST|PATCH /api/admin/llm/providers
POST /api/admin/llm/test           {providerId|'all'}
GET  /api/admin/llm/health-history
GET  /api/admin/content/pack       当前内容包只读视图 + 版本
POST /api/admin/sim/run            触发平衡模拟 {policy[], runs, seed}
GET  /api/admin/sim/report/:id     平衡报告（KPI 达标情况）
GET  /api/admin/runs/:id/replay    事件重放（调试）
```

SSE 事件：`narration-delta`（流式文本）/ `state-patch`（状态栏增量）/
`phase-advanced` / `done`。断线后前端用 `events?from=seq` 对账，不丢局。

## 9. 前端（packages/web，React + Vite）

- 三页：`/play`（GDD §13 三段式）、`/archive`（档案馆）、`/admin`。
- **服务端权威**：前端是渲染器 + 输入框，不持有任何规则逻辑；

- 管理后台：LLM 配置卡（路由 × provider 矩阵、key 输入、测试按钮、健康曲线）、
  内容包浏览、模拟触发与报告、对局回放。

## 10. 测试体系（本方案的重心）

金字塔从下往上，**每一层的测试都用游戏业务语言命名**；
TDD 流程：先写场景测试（红）→ 实现内核（绿）→ 内容调参 → 平衡报告。

### L1 单元测试（内核规则，Vitest）

每个状态机/公式独立测。示例：

```
✓ 饥饿：凌晨 tick 应使"正常"降为"饥饿"，"饱足"只降到"正常"
✓ 饥饿：濒死连续 2 天，转重病概率区间符合 50%±
✓ 交易：卡佳在场时收购价上浮不超过 +15% 上限
✓ 袭击：威胁值公式在 D30/家产200/加固2 时落在预设区间
✓ 检定：2d6+3 对难度 9 的成功分布（蒙特卡洛 10 万次断言分位）
```

### L2 不变量/属性测试（fast-check）

- **守恒律**：任何意图序列执行后，全物品流动记账守恒（无凭空增减）。
- **合法性**：状态转移只走声明的边（饥饿不会跳级、心情点数单调对应级别）。
- **确定性**：同 seed 同输入 1000 次重放，事件流逐字节一致。
- **快照一致性**：任意事件前缀折叠 == 对应快照。

### L3 业务场景 e2e（无头，内核 + 编排，无 LLM）

用**场景 DSL** 写，这是"从游戏业务设计视角覆盖 e2e"的落点：

```ts
scenario('熟食经济', s => s
  .given(队伍: ['布罗','埃米尔'], 库存: {生食: 8, 水: 8, 燃料: 4, 炉灶: 已建})
  .when(每天: ['埃米尔烹饪','布罗吃熟食'], 推进天数: 12)
  .then(生食耗尽天数 ∈ [10, 13])           // "隔天吃饭"压力带
  .and(无人低于"严重饥饿"))
```

首批 20 个场景直接从 GDD 数值表翻译（冬夜无暖生病率、绷带治疗时长、
41 天魔咒之日的老人们台词触发、灯塔广播后 3 天停火……）。

### L4 LLM 评测集（fixtures 回放，CI 必跑，零外呼）

- **意图解析集**：~300 条标注玩家话术 → 期望意图/拒绝。
  门槛：准确率 ≥ 92% 才允许对应提示词模板版本发布。
- **越界语料**：50 条作弊话术（"我口袋有 AK"…）→ 必须 100% 结构化拒绝。
- **封印泄漏集**：30 条社工套话（诱导说出白桦协议/灰雀身份），
  在未满足触发条件的上下文里 → 模型输出不得包含封印关键词（词面 + 语义双查）。
- **叙事一致性**：叙事文本中的数字必须与 facts 一致（对模板化事实做抽取断言）。
- 运行方式：录制的真实响应作 fixtures 回放断言；`npm run eval:live`
  连真实 provider 跑同套语料出对比报告（手动/夜间，不阻断 CI）。

### L5 数据成长与迁移测试

- 500 局合成数据（sim 直接入库）后：快照重建 < 2s、档案馆查询 < 200ms、
  run_event 表 ANALYZE 后查询计划无全表扫。
- 迁移测试：旧版本库 → 逐版本迁移 → 与新库 schema 一致且玩家域数据零丢失；
  内容包重种子化幂等。

### L6 全栈 e2e（Playwright，真实 Docker 镜像，LLM 用桩）

- 玩家旅程：开局 → 三句话玩法（含一次越界输入）→ 黄昏指派 → 夜间 SSE 叙事 →
  存档断点续玩 → 死亡入档 → 档案馆出现记录 → 第二局看到跨局痕迹。
- 管理旅程：配置 GLM provider → 连通测试通过 → 切路由 → 叙事继续（桩验证路由生效）。

## 11. 平衡模拟器（packages/sim）——"内核设计是否平衡"的回答

### 11.1 形态

- 无 LLM、无前端：机器人策略直接对 `core` 下意图，一夜 1 万局。
- 策略库（每个策略暴露一类平衡问题）：

| 机器人 | 行为 | 暴露的平衡面 |
|---|---|---|
| 守财奴 | 从不外出 | 袭击压力、静态经济 |
| 赌徒 | 每晚出门最险地点 | 死亡分布、检定难度 |
| 均衡策略 | 参考攻略式运营 | "会玩的人"生存曲线 |
| 老好人 | 有求必应、捐药 | 心情经济正反馈 |
| 恶魔 | 全偷全抢 | 道德成本是否过轻 |
| 档案学家 | 只奔文档点 | 主线节奏（文档发现率） |

### 11.2 KPI 门禁（阈值住在 `content/base/kpis.json`，改阈值也是受评审的内容变更）

| KPI | v0 目标带 | 检验什么 |
|---|---|---|
| 中位生存天数（纪实/均衡策略） | 28-35 | 一局时长设计 |
| ≥1 人活到停火比例 | 30%-55% | "挫折是内容但可赢" |
| 饿死占死因 | 15%-35% | 食物经济 |
| 冬季 vs 非冬死亡风险比 | 1.5-2.5 | 取暖机制存在感 |
| 袭击致全灭率 | <5% | 反纯随机挫败 |
| 每局文档发现中位数 | 3-6 | 层 1 需 8 份 → 2-3 局解锁 |
| 恶魔策略活到停火率 | < 均衡策略 -15pp | 道德有重量 |
| 单局 LLM 成本估算 | < ¥0.5 | 商业可行性 |

报告产物：Markdown + JSON（入库），含分布图；
PR 里贴 diff（"本次物价改动使饿死率 22%→31%，超出目标带"）。

### 11.3 门禁执行

- 触达 `core` 或 `content` 的 PR：自动跑 500 局快测（<2 分钟）；
- 夜间主分支：1 万局全量 + 分策略报告存档；
- KPI 越带 → CI 失败，允许在 PR 中**显式修改 kpis.json** 并附设计说明（评审定夺）。

## 12. 部署（单 Docker）

- 多阶段构建：`pnpm build`（web 静态产物 + server 打包）→ 运行层仅 Node 22 + better-sqlite3 原生依赖。
- 启动序列：迁移 → 内容包校验与种子化（失败拒启）→ 起 Fastify（API + 静态托管 + SSE）。
- `docker compose up` 即完整服务；卷挂载 `./data`（SQLite + 备份）；
  环境变量：`MASTER_KEY`（key 加密）、`ADMIN_PASSWORD`、`PORT`。
- 健康检查 `/healthz`（含 DB 可写、内容包版本、LLM 路由状态）。
- 升级 = 换镜像重启（迁移幂等）；回滚安全：玩家域向后兼容策略写入 ADR。

## 13. 迭代工作流（小块如何切）

每次变更的标准循环：

```
GDD/ADR 增补 → 场景测试(红) → 实现/内容改动(绿) → sim 平衡报告 →
PR 评审（设计 diff + 测试 diff + 报告 diff 三合一）→ 合并升内容包版本
```

里程碑切片（每片 ≤1 周量，均含测试）：

| 里程碑 | 交付 | 验收测试 |
|---|---|---|
| M0 行走骨架 | Docker + SQLite + 硬编码"第 0 天"场景 + SSE 文本流 | 1 条 Playwright e2e 绿 |
| M1 内核 | 状态机 + 日循环 + 事件溯源 + 场景 DSL | L1×60 + L3×20 |
| M2 探索 | 地点卡/时间槽/2d6/战斗 | L3 夜间场景 + 确定性重放 |
| M3 LLM 层 | 双 provider + 路由 + 意图解析 + 直读降级 | L4 评测集 + L6 管理旅程 |
| M4 内容与平衡 | 12 角色/14 地点/经济 + sim + KPI 门禁 | 首份平衡报告达标 |
| M5 档案馆与主线 | 跨局 + 封印协议 + 灯塔/入桌 | 跨局 e2e + 泄漏集 |
| M6 打磨 | 管理后台完善、回放器、成本报表 | 全量回归 |
